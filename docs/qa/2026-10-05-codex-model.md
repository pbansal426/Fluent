# Fluent model QA — 2026-10-05 — codex

Tested `http://localhost:8765/demo/app/`, build `2026-10-03.17`, with `google/gemma-4-e4b`. The final run confirmed both the model input and local-model picker had that model ID. Five independent conversations ran in the required order: 11, 11, 12, 12 and 12 typed turns (58 total). Language: English, as a non-native English speaker using both English and Spanish forms. Speech and hands-free listening were disabled through `?lang=en&speak=0&live=0`. No microphone was used. No application code, prompts or tests were edited; no model service was restarted or reloaded.

All names, dates and phone numbers were made up. The offered SSN `000-00-0000` is deliberately invalid test data. Screenshots show that same synthetic number so the visible-transcript defect can be reviewed. Assistant wording below is exact, including punctuation, line breaks and truncation; “Fill receipt” identifies a separate UI confirmation bubble.

Timing: start to settled UI was 7.24–9.65 seconds. Typed-turn completion was 1.81–3.63 seconds, median 2.82 seconds. Measurements include a 1.6-second stability check and 0.2-second polling, so these are conservative end-to-end UI times, not pure model latency. No error banner appeared on any recorded turn. Browser console showed a missing favicon (404), without a functional error.

Method: headless Chrome at 1100 × 1400 through the existing DevTools harness, using the actual app and real model. Sample selection, Start and Send used the DOM controls; fields were checked in the form iframe after each turn. No corpus or full e2e suite was run. The initial read-only browser probes overlapped a clinic Start probe briefly; the five recorded conversations themselves ran serially.

The first three inputs were ordinary name/date/phone information, adjusted for I-9’s surname-first layout. They were not forced into an expected field: on W-4 the third input deliberately exposes what happens when a birth date reaches the private SSN box; on I-765 ordinary information exposes incorrect field routing. These PDF forms did not follow a name/date/phone question sequence. The clinic runs used “I do not know”; the three PDF runs used the exact “I don't know” wording.

Judgments are qualitative: “plain” means understandable to a low-literate non-native speaker, rather than a measured readability score. “No invented value” means no unsupported personal value appeared in the checked fields; it does not mean routing was correct.

## Top 5 things that would stop a grandma

1. **Private-number handling cannot be trusted from the screen.** The same assistant that warns about an SSN asks for it in an ordinary box and leaves the number in the visible conversation.
2. **The form can silently contain the wrong answers.** I-765 stores a birth date in an attorney bar-number field and a current name as an alias. W-4 accepts a date as SSN and says it was saved.
3. **The next step is unclear.** “Is this part needed?”, “What is the next part of the form?”, and the I-9 claim that no phone field exists leave the user to interpret the form themselves.
4. **PDFs are hard to read at a glance.** Tiny official labels, dense W-4 translation badges and long choice strings overwhelm the simpler sidebar. The I-765 list cuts off before the sentence ends.
5. **Recovery and controls require too much guessing.** Repeated choices add little help; middle-name follow-ups change topic; samples require sideways scrolling; the composer has no persistent label and its controls are icons.

At 1100px, the chat bubbles have clear contrast and are easier to read than the PDF. The clinic’s form fields and orange focus outline are easier to follow. The PDF pane adds page buttons, Open PDF and Download filled PDF alongside sidebar controls and sample/upload controls. That is a lot to choose from for the target user. These are visual assessments from the saved screenshots, not a user study or measured contrast audit.

- Speech, microphone permissions and interruption were prohibited by the task and were not tested.
- Full completion, later PDF pages, saved-PDF download, real Chrome extension behavior and final form submission were outside these short conversations. No form was submitted.
- Actual non-native users, impaired vision, screen readers and keyboard-only operation were not tested. English comprehension was judged from wording; no formal grade-level score was calculated.
- No model change (brief section 9) was made: MODEL-TASK explicitly requests sections 6, 7, 8 and 5. No corpus run or provider/key testing was performed.
- All screenshots use 1100 × 1400. The separate 1280px/1024px/narrow-window sweep is brief section 4, outside this task. Sample-bar overflow and PDF readability were assessed at the tested size only.
- I did not capture model request bodies or inspect application history/log storage. A privacy warning is not proof that a number stayed out of all of them. The visible chat failure is directly confirmed.
- A tool output truncated about 139 tokens from one Spanish-clinic field snapshot, inside the sex/SSN/phone metadata. Exact replies and all turn boundaries survived; adjacent snapshots and the final screenshot confirm unchanged values. No conclusion depends on that omitted slice.
- `graphify query` was attempted before reading code; it failed because this worktree has no graph file. No code changes were made, so no graph update or `npm test` was needed. Initial failed Chrome-launch attempts did not produce model conversations; direct inline harness invocations worked.
